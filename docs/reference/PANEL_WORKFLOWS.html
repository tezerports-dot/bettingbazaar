1 · The spine every button hangs on

1.1 The order state machine

Nine states, and one rule table: ALLOWED_FROM in database/repositories/orders.core.js.

stateDiagram-v2

    PENDING_QUEUE --> ASSIGNED
    ASSIGNED --> PENDING_QUEUE : merchant declines

    PENDING_QUEUE --> PROCESSING : claimed from the open pool
    PROCESSING --> PAID : player asserts payment
    ASSIGNED --> PAID
    PAID --> COMPLETED
    PROCESSING --> COMPLETED
    DISPUTED --> COMPLETED : admin resolves
    PROCESSING --> DISPUTED
    PAID --> DISPUTED
    COMPLETED --> DISPUTED : a dispute can follow completion
    DISPUTED --> CANCELLED : resolved for the payer
    PAID --> CANCELLED
    ASSIGNED --> CANCELLED
    PENDING_QUEUE --> CANCELLED
    PROCESSING --> CANCELLED
    PAID --> FAILED
    ASSIGNED --> REJECTED

The guard lives in the UPDATE's WHERE clause. A caller arriving with a stale idea of the order matches no row and is refused. That is what makes an out-of-order provider callback safe rather than merely unlikely — the case a status field with no guard obeys silently.

Money moves with the state, in one transaction. A transition that produces an accounting event writes both together and records the ledger key on the transition row. Either the order advanced and the books recorded it, or neither happened.

order_transitions.tx_id is UNIQUE, so the same callback delivered twice collides INSIDE the transaction and the whole thing unwinds. There is no pre-read to race.

Two edges exist because they were missing and something broke. DISPUTED → COMPLETED: without it DISPUTED had no outgoing edges at all, so every admin resolution refused itself — the resolve route confirms the order is DISPUTED and then asks for COMPLETED, the guarded update matched no row, and it returned 409 for the one status those routes exist to handle. A disputed order could be created and never resolved. And ASSIGNED → PENDING_QUEUE (the requeue edge) turned the graph cyclic, which broke the default transition key: the second assignment of a rejected order collided on ord_<order>_ASSIGNED, was reported {ok: true, idempotent: true}, and the order stayed in PENDING_QUEUE still carrying the FIRST merchant's id.

The rail in force is payment_mode_policies — one ACTIVE version, append-only, justified. The rail an ORDER runs under is order_states.payment_mode, stamped at creation and immutable by trigger. Every worker and screen branches on the order's own value, never the current policy, so both rails run side by side after a switch until the last pre-flip order settles.

1.3 How an order reaches a merchant

A BUY is ASSIGNED, never claimed. tryAssignMerchant ranks the eligible merchants so the biggest holder takes the biggest order. Letting merchants claim a queued buy first-come rewarded whoever polled hardest and threw the ranking away.

A SELL may be claimed from the open pool, deliberately. A withdrawal nobody is free for waits in the open rather than burning retry attempts.

A cash BUY is matched to a link — a queue on the supply side, not a contest.

Eligibility asks the same questions on every path — assignmentCandidates, cashSuppliersFor, and the cash-link claim:

  • ACTIVE and APPROVED
  • online, and accepting this order's direction
  • this order's rail, and for USDT this order's chain
  • under both concurrency caps
  • not barred from this player by order_rejections
  • not assignment-paused (assignment_paused_at IS NULL)
  • able to fund it — proved by taking the hold, not by reading a balance

The cash-link claim asked none of these. It joined merchants not at all, under a comment saying so deliberately, so a merchant an admin had stopped kept being handed players through a link they had left behind. A link is supplied minutes before it is claimed: eligibility is a question about the claim, not about the supply.

1.4 The hold — why a check is not a lock

A merchant's tokens on a BUY order are HELD, in merchant_settlements (direction='DEPOSIT'), through depositEscrow.service.js. Taken at ATTACHMENT by all three routes that attach a merchant — auto-assignment, admin assign/reassign, and claiming from the open pool — released automatically on every terminal outcome, and consumed by the confirm. At most one live hold per order, enforced by merchant_settlements_one_live_deposit.

A guard you can pass twice is not a guard, however good its number is. The first fix for this made the assignment check read a MORE ACCURATE balance — available minus the orders already in flight — and left it a read. Two buy orders arriving in the same instant both passed it and were both assigned to a merchant who could fund one. Measured, not theorised. A number read in one statement and acted on in another is a snapshot no matter how good the number is. The guard is now in the UPDATE's own WHERE under a row lock, and the caller learns the answer from whether the write landed. Taking the hold IS the check.

Nothing else can reach held tokens. Every other movement touches available; reserved is reachable only through the settlement state machine. An admin deduction is legs: { available: -a }, so it cannot reach a player's promised tokens, and no production caller passes allowNegativeAvailable.

Why #4 exists. A buy is assigned, never claimed. The handler used to admit a PENDING_QUEUE deposit, which made an unassigned buy claimable first-come by anyone who knew its id — the only place on the buy side where two merchants could race. It also defeated the ranking that exists so the biggest holder takes the biggest order. The sell pool is deliberately different: a withdrawal nobody is free for waits in the open rather than burning retry attempts.

Why 11a and 11b are different codes. Losing a race is a CONFLICT and the merchant should try the next order; a shortfall is theirs to act on by topping up. Collapsing both into 400 told a merchant who had simply been outpaced that their balance was short.

The merchant record used to carry an activeOrderCount incremented on accept and decremented on finish; a crash between the two throttled that merchant permanently, with nothing able to correct it. And the order being accepted is subtracted from its own count — otherwise a merchant at a limit of 1 was assigned an order and then refused when they tried to accept it, blocked by the very order they were accepting.

On success, four things happen in this order, and the order is load-bearing:

  1. The order is requeued to PENDING_QUEUE and committed.
  2. The deposit hold is released. Before, not after, the reassignment — merchant_settlements_one_live_deposit permits exactly one live hold per order, so releasing afterwards would have the new merchant's hold refused as held_by_another: the order reassigned with nobody's tokens behind it and the first merchant's still locked.
  3. The refusal is recorded through merchantRefusal.service.js — the pair is barred (this order never returns to this merchant, and this merchant never sees this player again), the consecutive streak advances, and at maxConsecutiveRejections the merchant is SUSPENDED.
  4. Reassignment runs, and already sees the bar.

An EXPIRED assignment lands in the same function and counts identically. That is what stops a merchant refusing without limit simply by never pressing the button. A decline and a lapse mix: two lapses and a decline is three. Only a COMPLETED order resets the streak, and only an admin or sub-admin lifts the suspension — approveMerchant zeroes the count in the same statement, because a merchant reinstated while standing at the cap is re-suspended by the very next refusal and the admin's decision lasts one order.

2.3 Dashboard — /dashboard

Dashboard.tsx. Six endpoints: the live order list, stats, earnings, the settlement-rail banner, the outstanding CDM-slip list, and online-status. There is no button here the order card does not also carry — the dashboard renders the same OrderCard, wired to the same useOrderActions, which is why the two cannot behave differently.

The rail banner reads the merchant's own rail on load (GET /api/merchant/payment-mode), not a socket event: a notification can be missed and a socket can drop, but the panel always loads.

Every count on this screen is derived from rows. Active order counts come from getActiveOrderCounts, which reads the orders; earnings come from the commission ledger. Nothing here is an accumulator — an accumulator counts passes, not rows, and a crash mid-pass loses the count permanently while the money stays correct.

2.4 History — /history

HistoryViews.tsx. Read-only: completed orders, earnings, and weekly earnings. Three endpoints, no writes. The only interactive elements are filters and copy-to-clipboard.

2.8 What the merchant is NOT shown

A merchant sees the bank account a withdrawal pays and the name on it. Nothing else identifies the player — not the phone number in whole or in part, not the UPI ID (which resolves to both), not a CDM receipt after submission.

This was a denylist that deleted the player's payout destinations only on the DEPOSIT branch, so on every withdrawal the merchant received the player's UPI ID — and the panel had a render waiting for it, while its order search matched on the player's phone number. It is now an allowlist in one file, domains/merchant/merchantOrderView.js, and the tests assert the response's key set is a SUBSET of it, so a new leak fails without anybody adding a line. npm run check:merchant-privacy.

3.6 System settings — /settings

SystemSettings.tsx → GET/PUT /api/admin/system/config. isAdmin to write; isAdminOrSubAdmin to read.

Before that it was three hand-written lists that disagreed: twelve merchantOrderLimits fields declared and four writable; withdrawalHoldMinutes, both loadShedding ceilings and all eight ipDefense fields read by live middleware and reachable from nothing — two of them under a comment calling them "admin-editable"; and the one-minute board's four phase offsets, run by the engine and invisible to both halves. maxConsecutiveRejections was the sharpest: returned by the GET and dropped by the PUT, so it rendered on this screen, accepted typing, said "saved" — and the next merchant refusal was judged against the old cap.

4 · The player panel

The one with the most users and the least authority. A player can buy tokens, sell them, bet, and dispute. That is it.

4.1 Getting in

Signup is in the Telegram bot, not here. The panel's AuthModal logs in an account the bot created.

KYC is a 12-digit Aadhaar number, held as an HMAC plus AES-256-GCM ciphertext. No document is collected, stored or accepted — do not add an upload path for one. There is also no player email; the bot never asks for one. (SupportLinks.email and merchants.email are different things and stay.)

PENDING_APPROVALyesnoYour Aadhaar is being verified. This is done in batches and needs nothing from you — you will be able to play as soon as it clears.

Buying takes requireLinkedKyc; selling takes requireApprovedKyc. The asymmetry is deliberate: a player whose Aadhaar is queued for a batch check can put money in, because the platform holds it either way; taking money out waits for the check.

An APPROVED Aadhaar is immutable. A REJECTED one may be replaced through the bot up to MAX_KYC_SUBMISSIONS. A FAILED submission's row is DELETED — aadhaar_hash is unique, so a typo would otherwise park a stranger's Aadhaar in that index and lock its owner out forever.

The cool-off is a database timestamp, not a cron. users.order_lock_until is written by the DATABASE's clock, so it expires on its own with nothing to fail, and GREATEST extends rather than shortens. Nobody is auto-blocked by it. The player is flagged for an admin. The only blocking path is an admin pressing Block, which itself requires a reason.

USDT is one token on several chains

A USDT buy is denominated in platform tokens — exactly 50,000, 100,000 or 500,000 — and what the player sends is DERIVED from the admin's rate at creation. There is no second denomination list, because the rate is admin-editable and a stored USDT amount would be a second owner that drifts the moment it changes.

The quote is the contract. rate_used and fiat_amount_paise are written WITH the order and frozen by trigger. Assignment used to re-read the rate, so an admin edit in between silently re-priced a purchase the player had already agreed to.

The player picks the network first, before an order exists, because it decides which merchants can serve it. The address and its network always travel together — in the snapshot, in payTo, on the screen. USDT sent to a Tron address from a BNB Smart Chain wallet is gone, and it is the only unrecoverable mistake this platform can make.

The escrow debit IS the gate, and it is the whole gate. Winnings → locked, under SELECT … FOR UPDATE on the wallet row, in one transaction with its ledger entry, idempotent on wd_<id>. 4.5 What the player is NOT shown

A player sees where to pay and nothing about who they are paying — a payment link, an opaque Merchant #<ref>, a deadline.

Every player-facing response used to carry merchantSnapshot whole — the merchant's UPI handle, QR, bank account number, IFSC, account-holder name and USDT address — on creation, fetch, dispute, assignment push and every status poll. A player could copy and keep a merchant's account number from one deposit. It is now an allowlist in one file, domains/payment/playerOrderView.js, asserted as a key-set SUBSET so a new leak fails without anybody adding a line. npm run check:player-privacy.

Stated honestly: a upi://pay intent carries the payee, so the payer's own banking app will show it. The platform stops publishing the merchant's identity; it cannot hide a payee from a payer.
