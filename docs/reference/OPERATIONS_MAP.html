How to read this

MONEY MOVED a balance changed and a ledger row exists.

WAITING the row is parked; something else must act.

REFUSED nothing moved; the caller was told why.

F-0NN a recorded defect on this path. See the audit register.

Every route, guard, job name and state below was extracted from the code, not written from memory. Where a flow has a known defect it is marked in place rather than described as working. Where something was not verified, it says so.

The order state machine

Nine states, enforced by a CHECK constraint. Every transition is a guarded UPDATE — the state it expects is in the WHERE clause, so two callers racing produce one winner and one REFUSED, never two.

stateDiagram-v2
  [*] --> PENDING_QUEUE: player creates
  PENDING_QUEUE --> ASSIGNED: auto-assign / admin / merchant accepts
  PENDING_QUEUE --> CANCELLED: expiry cron
  ASSIGNED --> PROCESSING: merchant starts
  ASSIGNED --> CANCELLED: expiry / merchant rejects
  PROCESSING --> PAID: player submits UTR (deposit)
  PROCESSING --> PAID: merchant asserts sent (withdrawal)
  PROCESSING --> CANCELLED: expiry
  PAID --> COMPLETED: money moves, then this
  PAID --> DISPUTED: player disputes
  PROCESSING --> DISPUTED: merchant disputes
  COMPLETED --> DISPUTED: merchant only
  DISPUTED --> COMPLETED: admin releases
  DISPUTED --> CANCELLED: admin refunds
  COMPLETED --> [*]
  CANCELLED --> [*]
Asymmetry worth knowing

A merchant may dispute from PROCESSING, PAID or COMPLETED. A player may dispute only from PAID — if (order.status !== 'PAID') return 400. So any bug that moves an order out of PAID without paying the player also removes their only recourse. That is exactly what F-017 was.

The ordering rule, now uniform

Money moves before the status does, on every deposit path. Each movement is keyed on the order id, so a refusal or a crash leaves a PAID order the next attempt replays as no-ops — retryable, and still disputable. The reverse ordering shipped four times in this codebase before it was made uniform.

Player workflows

The player never sees who they are paying — a payment link, an opaque Merchant #ref, a deadline. Everything below is what they can actually reach.

Signing up

Telegram bot → no password, no email

Why the ceilings exist

₹10,000 is the most a cash machine dispenses in one go and ₹40,000 the largest denomination it handles — so they bound the CASH_ATM rail and one payout leg. Neither applies on UPI and neither applies to USDT. They were once enforced on every INR buy: a machine's limit applied where there is no machine.

F-018 · open · the root cause

Reaching the merchant not funded branch at all should be impossible. Eligibility is checked on all three assignment paths — but it is a snapshot, not a hold. The tokens stay spendable, so between assignment and confirmation they can go to another deposit, a withdrawal payout or an admin deduction. The wallet already has reserveForSettlement / completeReservation / cancelReservation to hold them. Nothing calls them.

The hold is the whole design. The merchant asserting payment settles nothing. Until the window passes neither side has moved, so a dispute is a reversal rather than a clawback. This branch previously consumed the stake and credited the merchant in the same request — a merchant who pressed confirm without sending money held spendable tokens instantly.

A withdrawal larger than one payout leg is split, never refused. The siblings share a withdrawal_batch_ref, which two admin screens read.

Two traps this path already paid for

The winner is written before the status, and a cycle with no winner is never offered for settlement — otherwise the engine looks healthy and silently never settles. And the payout figure is net: the function returns {gross, fee, net} and has no payout key, so p?.payout ?? 0 pays zero while still charging the fee.

Real pool totals are derived from the bets table and never stored on the cycle row — a bet holds a share lock there, so a bet that also updated it would deadlock against another bet.

F-018 · this is where it bites

All three doors check the balance and none of them holds it. The check is true at the moment it is made and nothing keeps it true until the merchant confirms.

What freezes at assignment and can never be re-decided later: the USDT chain, the quote (rate_used and fiat_amount_paise), and the rail the order runs under — all by database trigger. Assignment used to re-read the USDT rate, so an admin edit in between silently re-priced a purchase the player had already agreed to.

The merchant's rejection proof is never shown to the player — it can be a bank statement with their name on it. The player gets the reason, not the image.

A CDM slip, a UTR and a chain transaction hash are the same fact — this payment happened, once — so they share one registry. Two of the three used to write the reference into a column and claim nothing, so the same slip could be presented twice.

Verified — and this is the subtle part

Both panels read the live policy for a new order and the order's own frozen mode for an existing one. Getting that backwards would silently rewrite the rules of orders already in flight. The merchant banner also re-reads rather than rendering the pushed payload, so one owner decides what the rail is.

The rail in force is not a feature flag — a flag is an env var and an in-process Map, so it cannot survive a restart or say which rail was live when an order was created.

This queue was permanently empty for a period: the panel called a path the server never served, the component caught the 404 and rendered its empty state — indistinguishable from "no disputes". What each side is never told

privacy points both ways
DirectionAllowedNever
Merchant → about the playerthe bank account a withdrawal pays, and the name on itphone in whole or part, UPI ID (it resolves to both), a CDM receipt after submission

Both projections are allowlists in one file each, and the tests assert the response's key set is a subset — so a new column added to the orders table cannot leak by default. A denylist admits the next field automatically and its mistake is always "too much"; an allowlist fails closed and its symptom is a blank field somebody notices.

Stated honestly

A upi://pay intent carries the payee, so the player's own banking app will show it. The platform stops publishing the merchant's identity; it cannot hide a payee from a payer.

What runs on its own

Eleven scheduled jobs, an optional Redis, and a realtime layer. Nothing here needs a person, and several of these are the only thing standing between a stuck row and a lost balance.

The one to check by hand

order-expiry deliberately does not touch PAID. That is correct — auto-cancelling an order the player has already paid for would strand their money. The consequence is that anything which leaves a row stuck at PAID is never swept, and only a person can clear it. That is why the not-funded branch alerts.

BullMQ is used for one thing only: scheduling the eleven recurring jobs. The one-off enqueue() API exists, is tested, and is called by nothing in the backend — the same shape as F-018, found while building this map.

Realtime

36 event names across three transports

socket.io for public browser clients, SSE for authenticated private streams, and the emitter module. One name per logical change, unique across all three — a name reused on a different transport for a different meaning is the defect this rule exists to stop.

  • Two silent dead-delivery traps live here. emitMerchantUpdate('*', …) reaches nobody — it looks the literal '*' up as a merchant id and returns, with no error and no log. Use the broadcast helper.
  • The panel's SSE client registers listeners from a hardcoded name list, so a subscriber for an unlisted event never fires and never errors. A new event must be added to that list as well as emitted.

What this map is not

It is derived from the code, but it is a reading, not a proof. Reading is what missed every one of the defects above until somebody asked a harder question. Four questions found them, and they are the ones to bring to any flow here: does anything actually call this · is this check a snapshot or a guarantee · if it fails halfway what does the row say · am I fixing the symptom or the cause?
