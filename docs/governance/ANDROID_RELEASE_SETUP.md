# Android release: keystore, secrets, first build

Three things gate the first APK, and **all three are yours to do** — not
because they are hard, but because doing them for you would compromise them.

The signing keystore is the identity of your app on every Android device that
ever installs it. If it is generated by anyone but you, or ever passes through
a repository, a chat log, or a CI log, it should be considered burned. There
is no rotation: **lose this key and you cannot ship an update to an existing
install, ever.** Users must uninstall and reinstall, losing local state, and
a Play listing cannot be recovered at all without Google Play App Signing
enrolment.

So: generate it on your machine, back it up offline, and paste it into GitHub
Secrets once.

---

## 1. Generate the upload keystore

On your own machine (needs a JDK — `java -version` should print 17 or newer):

```bash
keytool -genkeypair -v \
  -keystore upload-keystore.jks \
  -keyalg RSA -keysize 4096 -validity 10000 \
  -alias bettingbazaar-upload
```

It will ask for:

| Prompt | What to enter |
|---|---|
| Keystore password | A long random password. **Save it in your password manager now.** |
| Key password | Press Enter to reuse the keystore password — simpler, and no weaker. |
| First and last name | Your company or app name, e.g. `Betting Bazaar` |
| Organizational unit / Organization | Your company name |
| City / State / Country code | Real values; `IN` for India |

`-validity 10000` is ~27 years. Play rejects keys that expire before 2033, and
you cannot extend one later, so do not shorten it.

### Back it up before doing anything else

```bash
# Verify it exists and note the SHA-256 fingerprint for your records
keytool -list -v -keystore upload-keystore.jks -alias bettingbazaar-upload
```

Copy `upload-keystore.jks` **and** both passwords to at least two places you
control that are not this laptop — an encrypted password-manager attachment
and an offline backup are the usual pair. Do not put it in the repository;
`.gitignore` does not protect you from `git add -f`.

## 2. Set the six GitHub secrets

`Settings → Secrets and variables → Actions` on
`tezerports-dot/bettingbazaar`.

### Four repository **secrets**

First turn the keystore into base64 (it is binary; secrets are text):

```bash
# macOS
base64 -i upload-keystore.jks | pbcopy

# Linux
base64 -w 0 upload-keystore.jks
```

| Secret name | Value |
|---|---|
| `ANDROID_KEYSTORE_BASE64` | The base64 blob from above, as one line |
| `ANDROID_KEYSTORE_PASSWORD` | The keystore password |
| `ANDROID_KEY_ALIAS` | `bettingbazaar-upload` |
| `ANDROID_KEY_PASSWORD` | The key password (same as the keystore password if you pressed Enter) |

`-w 0` matters on Linux: without it `base64` wraps at 76 columns and the
newlines corrupt the secret. The workflow will fail at `base64 -d` with an
unhelpful error.

### Two repository **variables**

These are *variables*, not secrets — same page, "Variables" tab. They are
public URLs, not credentials, and the workflow reads them as `vars.*`
(`android-release.yml:63-64`).

| Variable name | Value |
|---|---|
| `ANDROID_API_URL` | Your backend origin, e.g. `https://api.yourdomain.com` |
| `ANDROID_MERCHANT_PANEL_URL` | Merchant panel origin, e.g. `https://yourdomain.com/merchant` |

> Getting `ANDROID_API_URL` wrong is the single most common cause of an APK
> that installs and then shows a blank screen or "network error" — the app is
> fine, it is talking to the wrong host. It is baked in at build time, so
> fixing it means a new build.

## 3. Run the workflow

`Actions → Android Release → Run workflow`.

It takes a `version_name` input (e.g. `1.0.0`). This is the string users see.
The `versionCode` — the integer Play uses to order updates — is derived from
the run number and **must increase on every upload**; the workflow handles
that, which is why you should build through it rather than locally.

The APK/AAB appears as a workflow artifact when the run finishes (~5–10 min
for a cold cache).

### Install on a real phone

```bash
# Enable Developer options -> USB debugging on the phone, then:
adb install -r app-release.apk
```

Or transfer the APK and tap it, allowing "install from unknown sources" once.

## What to check on the device

Beyond "it opens":

1. **It reaches your backend.** Log in. A blank screen or spinner means
   `ANDROID_API_URL` is wrong.
2. **Origin failover works.** The app tries each configured domain until one
   answers (`user-panel/src/services/originFailover.ts`). Verify it recovers
   when the primary is unreachable.
3. **Socket reconnects after backgrounding.** Background the app for a minute,
   reopen it, and confirm live cycle data resumes — that is what PR #97 fixed
   and it only reproduces on a real device.
4. **2FA.** If your admin account is enrolled, the login should ask for a code.

## If you plan to publish on Play

Enrol in **Google Play App Signing** at first upload. Play then holds the real
app-signing key and yours becomes only an *upload* key — which means a lost
upload key can be reset by Google instead of ending the app's life. It is the
single most valuable safety net available here, and it can only be chosen at
first upload.

Separately: a real-money betting app will be reviewed against Play's gambling
policy, which requires a licence in each target country and geo-restriction to
those countries. That is the same §G licensing gate in
`LAUNCH_READINESS.md`, arriving from a different direction.
