2. THE 14 HANDOFF ITEMS
--------------------------------------------------------------------------

Each was reproduced on the old code before it was fixed. "Before" is what
the old code actually did when tested.

A1  The order tamper tag was never written (F-024)
    Before: an order with its tag stripped was still accepted (200).
    Fix:    the tag is written when the order is created; the guard now
            refuses an order without one.
    Proof:  M156, M165, M92.

A2  A retried withdrawal locked winnings with no order behind them (F-025)
    Before: 2,000 locked for a single 1,000 withdrawal.
    Fix:    the lock and the order are written in one transaction.
    Proof:  M166, M118.

A3  Every confirmed buy charged the merchant twice (F-026)
    Before: a 1,000-token buy cost the merchant 200,000 paise instead of
            100,000, and a merchant whose tokens were all held was refused.
    Fix:    the merchant's tokens are taken once, from the hold.
    Proof:  M167, M168.

A4  Admin and dispute endings of a withdrawal were wrong in 10 of 11 cases (F-027)
    Before: locks left standing; a cancelled dispute went back into the queue.
    Fix:    one function decides how every admin ending moves the money.
    Proof:  M169, M170, M171.

A5  A confirm with nothing held settled after it had already committed (F-028)
    Before: not reproduced failing (its test already passed); fixed from
            reading the code.
    Proof:  M172.

A6  Test assertions that compared NaN with NaN passed for any value (§32 S40)
    This is why A3 had stayed hidden.
    Fix:    every test config now refuses such an assertion.
    Proof:  M173.

B1  The dead-code check counted comments as callers
    Before: it reported 0 dead items; with comments ignored it found 12
            dead exports and 1 dead module.
    Fix:    all deleted, and the check now ignores comments.

B2  The IP deny-list never ran (F-030)
    Before: nothing mounted it, called it, or showed it on a screen.
    First deleted, then on your instruction REBUILT PROPERLY:
      - an ip_blocks table;
      - middleware that runs before every limiter;
      - admin routes that refuse to block your own address, loopback, or
        too-wide ranges;
      - a Blocked IPs screen;
      - route, page and penetration-test checks.
    Proof:  M183 to M187.

B3  A setting the platform does not know came back as a server error, not a
    plain refusal
    The same sweep found two more cases that answered 500 for a request
    that should be refused.
    Proof:  M174, M175, M176.

B4  The PAN registry had no caller
    Fix:    deleted.

C1  An order could be stamped with a payment method it was never checked
    for (F-031)
    Before: an order checked as a cash order was saved as a UPI order.
    Proof:  M180.

C2  The cash matcher followed whichever payment method was switched on now,
    not the one the order was made under (F-031)
    Before: a waiting cash order was abandoned (0 matched).
    Proof:  M179.

C3  A dispute raised while the payout worker was settling was settled
    underneath (F-029)
    Before: the order ended COMPLETED instead of DISPUTED, and the money
            moved.
    Proof:  M177, M178.

C4  Android uploads
    - A "zip bomb" APK inflated 64 MB inside the server process. Now bounded.
    - Two uploads of the same version at once: the loser answered 500 and
      left its file behind. It now gets a plain refusal and its file is
      removed.
      Proof: M181, M182.
    - P197-5 was not a defect: on Android, each app has its own cookie
      store.
    - P197-1 (the APK signature was not verified) was first documented as a
      known risk. It is now fixed as R7.

Also found while working the handoff: a test that failed at random
("cashLinkRoutes"). The cause was a different test leaving ₹40,000 cash buys
behind. That is fixed, with a test that fails without the fix.

R7  "APK signature verification"
    Every uploaded APK's signature is now verified the way Google's
    apksigner verifies it: the contents, the signature, and that the
    certificate is the key that signed. This was proven against APKs signed
    by Google's real apksigner (RSA and EC keys, v2 and v3 schemes), and
    against tampered copies. A forged or altered APK is refused at upload,
    before it can be published.                          M211, M212, M213

R9  "proper admin control of the APK"
    - Halt / Resume a published release. A broken build stops being offered,
      downloaded or required at once, and phones go back to the previous
      release.
    - Android-version safety. A phone is never offered a release its
      Android can't install. Below a mandatory release it can't install, it
      gets a clear "your Android is too old" screen instead of an endless
      update loop.
    - The release card shows the Android a build needs, that its signature
      was verified, who uploaded, published or halted it, and a Download APK
      button. It warns when a new build needs a newer Android.
    One gap was caught by the new tests before it shipped: an upload below
    a halted release would have been accepted.
    The new Java code compiled in CI's Android build.        M214 to M218

5. HONEST NOTE ON WHY DEFECTS KEPT APPEARING
--------------------------------------------------------------------------

Most defects were not wrong calculations. They were:
  - checks that measured the wrong thing;
  - tests that asserted something that was always true;
  - one guard placed in only some of the paths that needed it;
  - screens that hid a failure behind an empty state.
They passed every check that existed at the time. They were found by
running the code against a real database and a real browser, and by
forcing the race conditions to happen instead of hoping they would.
Each kind of defect found is now written into CLAUDE.md §32 (S40 to S44),
with the question that finds it.
