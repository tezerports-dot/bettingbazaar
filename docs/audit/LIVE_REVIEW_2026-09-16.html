Money paths that could not complete 3 findings · all now verified end to end

Each of these is a total outage on a path real money travels. None of them showed up as a failing test, because in every case the two halves passed their own tests and it was the pair that was broken.

Tokens moved, not minted — both sides of the ledger checked, not the status.

Transactions — a type that lied about every field

admin-panel/src/types.ts §23 49551aa
Was
TypeError: Cannot read properties of undefined
             (reading 'slice')      ← tx._id.slice(-10)

The endpoint returns wallet ledger rows. The panel's Transaction interface was a fossil of the document collection it replaced:

declared      actually sent
────────      ─────────────
_id           (none — the id is txId)
status        (a ledger row has no status)
balanceType   field
referenceId   refId
description   reason
timestamp     createdAt

TypeScript could not catch any of it, because the interface was the thing that was wrong.

Now
/transactions   chars=12,439   [ok]

Fixed the way §23 prescribes: correct the interface, let tsc enumerate the call sites. It listed 18, all in one file.

The filters were fossils too, and failed silently: the type tabs sent DEPOSIT where tx_type holds CREDIT, emptying the table rather than erroring; the Status dropdown mapped to a parameter the route has never read; and all three KPI tiles read ₹0 on every page of a busy ledger.

Same root, one level down: DataTable's rowKey tried userId first. Right for the users table where it is the identity — wrong for any row that merely references a user. One player owns many ledger movements, so the whole page rendered with one key repeated down the table. Duplicate keys let React reuse the wrong row across an update, on the screen an operator reconciles money from.

A merchant could overwrite the player's claimed payment reference

§27efe3a2a
Was

The confirm took utrNumber from the request body and wrote it over the stored value. The reference is the player's — claimed against that order in utr_registry for good.

merchant posts {utrNumber: '999999999999'}
→ order names a reference nothing ever claimed
→ the claim still points at the player's original
→ the merchant's string free to spend again

The panel echoed the stored value back, so it never showed. A panel is not the guard.

Now

The route reads the row and refuses if the reference is not there. The body is not read at all; confirmPayment sends none.

merchant posts {utrNumber:'999999999999',
                proof:'…forged.jpg'}
→ 200, and the stored UTR is unchanged
→ proofScreenshot still null

A gate that was lying

check:orphans exists to catch exactly the bet-placement bug, and reported "No orphaned references" over it. Its blind spot was documented in its own header — and the cost turned out to be higher than the note anticipated.

scripts/detect-orphan-refs.mjs

§28 — derive what a gate checks from the thing it is checking
Was

No scope analysis: every binding anywhere in a file counted as visible everywhere in it. So the phantom handler's totalDelhi "covered" the real handler's use of the name.

$ npm run check:orphans
No orphaned references: every identifier used is
declared, imported or a parameter.
$ echo $?
0

The reasoning was sound — "a false report costs a bug" — it just cost more than a later run.

Now

A real scope chain: module, function and block scopes; var and function declarations hoisted; declarations and references resolved in one pass so forward references work without an ordering rule.

   1  totalDelhi   [declared in a DIFFERENT scope]
        bet.routes.js:512
   1  totalBombay  [declared in a DIFFERENT scope]
   1  realNow      [declared in a DIFFERENT scope]
$ echo $?
1
The false-positive bar is kept, and met differently. A file whose scoping is not statically decidable is skipped by name in the output rather than guessed at, and the two findings are reported separately — a name bound nowhere is a deleted import, a name bound in another scope is a block copied between functions. Clean across backend/ and database/, so the sweep for this shape is now mechanical rather than a one-off grep. §0.13

The honest answer to "is it ready"

No individual green check says so, and this run is why. Before today, CI was green while a player could not deposit, could not bet without being told it failed, and could not sign in from the button marked Sign in. What changed is not that the checks got greener — it is that three money paths were driven from end to end by hand and now have their balances written down.

What I verified: the buy rail, the sell rail, bet placement, admin 2FA, merchant onboarding, both privacy projections, and that 65 of 67 screens render clean in a real browser. What I did not: the cash rail, the USDT rail, and dispute resolution — read, not run. That gap is the next piece of work, and it is the same gap that hid every defect above.
